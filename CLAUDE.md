# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Setup (Windows; `venv` already exists at the repo root):

```
python -m venv venv
venv\Scripts\activate
pip install -r requirements.txt
```

Copy `.env.example` to `.env` and set `FINNHUB_API_KEY`, `ALPACA_API_KEY`, `ALPACA_SECRET_KEY`, `ANTHROPIC_API_KEY`. AWS credentials for DynamoDB persistence come from the standard boto3 credential chain (env vars / `~/.aws/credentials` / IAM role) — only `AWS_REGION` needs setting explicitly in `.env`; set `DYNAMODB_ENABLED=false` to run without AWS credentials at all. `scripts/dynamodb-iam-policy.json` has a least-privilege IAM policy (create/describe/put/get/delete/scan, scoped to just the four tables below) for the IAM user whose access key goes into the boto3 credential chain — don't grant broader DynamoDB access than that.

One-time DynamoDB table creation (see `src/data/db.py`):

```
venv\Scripts\python.exe -m scripts.setup_dynamodb
```

Run (executes real paper trades against Alpaca during market hours — see Architecture):

```
python -m src.main          # loop forever, one cycle every RUN_INTERVAL_MINUTES
python -m src.main --once   # one cycle, then exit (manual test run)
```

Everything is logged to the console and `logs/trading.log`. Don't call `run()` from a bare `python -c` — that skips `setup_logging()` and you'll see almost nothing; use `--once`. Don't run `--once` while the loop is also running: with `DYNAMODB_ENABLED=false` each process keeps its own in-memory daily trade counter, so two processes can together exceed `MAX_DAILY_TRADES` and trade the same signal twice.

There is no test suite, linter, or formatter configured in this repo (no `pytest`/`ruff`/`flake8` config, no CI). Verify changes by importing the touched module directly, e.g. `venv/Scripts/python.exe -c "import src.trading.risk"` — the system `python` on PATH will not have `alpaca-py`/`anthropic` installed, only the venv's will.

## Architecture

Pipeline, one full cycle per ticker in `STOCKS` (`src/config.py`), driven by `src/main.py`:

```
market history (yfinance) -> technical indicators -> news (Finnhub company-news)
  -> Claude signal generation -> risk evaluation -> live quote (Finnhub, yfinance fallback) -> Alpaca paper order
```

- `src/main.py`: `run_forever()` is the process entry point — an infinite `time.sleep(RUN_INTERVAL_MINUTES * 60)` loop around `run()`, with no external scheduler dependency. Each `run()` call, in order: rolls `src/utils/monitoring.py`'s daily summary over if a new Eastern trading day has started; no-ops entirely outside regular NYSE hours (`src/utils/market_hours.py`'s cheap local pre-filter, Mon–Fri 9:30–16:00 America/New_York); builds the Alpaca client and runs `monitoring.check_alpaca_health()`, skipping the *entire* cycle if Alpaca itself is unreachable; confirms via `is_market_open_per_alpaca()` that the exchange is actually open today (holidays/early closes); calls `src/trading/positions.py::check_open_positions()` to close any position that has breached stop-loss/take-profit/trailing-stop; checks the daily loss limit, which only blocks the *search for new trades* below, not position protection above; runs `monitoring.run_health_checks()` (Finnhub + Anthropic only — see "Health-check ordering" below for why Alpaca isn't part of this call) and, only if that passes and today isn't loss-halted, loops `analyze_stock()` over every ticker. Position monitoring always runs ahead of and independent of the daily-loss-limit gate and the Finnhub/Anthropic check, so a halted day or a Finnhub/Anthropic outage still protects existing positions — only the search for *new* trades stops.
- `src/analysis/technical.py` + `src/data/market.py` + `src/data/news.py` + `src/data/finnhub_client.py`: pure data-gathering, no trading logic. `technical.py::calculate_indicators()` raises `ValueError` if any computed indicator is non-finite (NaN/inf) — RSI divides average gain by average loss, which is 0/0 for a stock with zero net price movement across the window, and that NaN would otherwise sail past every length check and reach Claude's prompt as the literal text "RSI (14-day): nan". This folds into the same data-quality failure path as insufficient history, so `main.py`'s existing per-ticker exception handling just skips that stock for the cycle. `calculate_volume_analysis()` drops yfinance's last daily bar when it's today's still-forming session (`_last_bar_is_in_progress()`): during market hours — the only time this system runs — that bar holds only partial-day volume, which made the ratio read as "low conviction" on every ticker every cycle and dragged Claude's confidence down. The other indicators deliberately still use today's bar, since its close is the current price. `market.py::get_market_data()` still pulls historical daily bars from yfinance — Finnhub's `/stock/candle` endpoint has moved behind a paid plan for US equities, so there's no free replacement for the multi-day history `technical.py`'s indicators need. `market.py::get_live_price()` and `news.py::get_stock_news()` both go through `finnhub_client.py`, which wraps the Finnhub SDK with rate-limit-aware exponential backoff (1s/2s/4s) on 429s and logs every call via `monitoring.log_api_call()`. `get_live_price()` falls back to yfinance's last close if Finnhub fails for any reason; `get_stock_news()` has no fallback and just propagates the failure (same as the old NewsAPI integration), which `analyze_stock()` in `main.py` already catches and treats as "no headlines this cycle."
- `src/analysis/signals.py::generate_signal()`: sends indicators + last-4h headlines to Claude (`client.messages.parse` with a pydantic `output_format`, model `claude-opus-5`, `max_tokens=16000`, `output_config={"effort": "low"}`) and gets back a structured `TradingSignal`. Opus 5 runs adaptive thinking whenever `thinking` is omitted, and that thinking draws from `max_tokens` — a tighter budget risked truncating the structured output on what's really a small classification task, hence the generous token ceiling paired with low effort to keep latency and cost down across 12 tickers every cycle. The system prompt is an f-string that reads `MIN_TRADE_CONFIDENCE` from `src/config.py` at import time rather than hardcoding it, so the model's stated execution-gate threshold can never drift from the actual gate in `risk.py`. Every call logs its token usage via `monitoring.log_claude_usage()`; an `anthropic.RateLimitError` is caught, logged clearly, and re-raised so `main.py`'s existing per-ticker exception handling skips just that one stock for this run. The signal's `risk_level` (LOW/MEDIUM/HIGH, Claude's own volatility-based read per `_SignalOutput`'s docstring) is advisory only — logged for a human reviewing trade history, but nothing in `risk.py` or `executor.py` reads it; sizing is driven entirely by `confidence`. Don't confuse it with `config.py`'s `RISK_LEVEL`, an unrelated global dial that happens to share the name. Wiring the signal-level field into sizing would be a live trading-behavior change made on an unvalidated hypothesis — do it deliberately, once there's real trade history to check it against, not as incidental cleanup.
- `src/trading/risk.py`: `evaluate_signal()` runs a short-circuiting sequence of checks (market hours → daily loss limit → confidence threshold → daily trade count → open position limit), each deferred behind a lambda so a check after an earlier rejection never actually executes — this matters because `check_daily_loss_limit` sets the day's baseline equity and can latch `halted_for_loss` as a side effect, and must not run on a signal already rejected for being out of hours. Returns a `RiskDecision`. Position sizing (`get_position_size_pct`) scales `MAX_POSITION_SIZE_PCT` by a confidence bracket from `CONFIDENCE_POSITION_SIZE_TIERS` (higher-confidence signals get a larger fraction). Daily trade count and daily-loss-limit state live in a module-level `_DailyState` singleton, keyed off the Eastern calendar date.
- `src/trading/positions.py::check_open_positions()`: runs every cycle before new signals are evaluated. Tracks per-symbol trailing-stop activation in an in-memory `set`; once a position's unrealized gain hits `TRAILING_STOP_TRIGGER_PCT`, its effective stop moves to breakeven for the life of that position. The trailing-stop flag (and its DynamoDB row) is cleared only once `_close_position` reports a confirmed `FILLED` exit — a rejected, errored, or still-pending exit leaves the position open and leaves the flag alone, since clearing it early would silently revert the stop from breakeven back to `-STOP_LOSS_PCT` on the next cycle, right after the exit had already failed once.
- `src/trading/executor.py::execute_signal()`: the single entry point from the AI layer to a real order — runs `evaluate_signal`, prices the order via `market.py::get_live_price()` (Finnhub `/quote`, falling back to yfinance), sizes via `calculate_position_size`, submits a market order to Alpaca (`paper=True` is hardcoded; there is no live-trading path), and polls briefly for fill status. Every outcome (SKIPPED/REJECTED/FILLED/PENDING/ERROR) is returned as a `TradeResult` rather than raised, so one bad signal never kills the loop over tickers.
- Both `executor.py` (signal-driven trades) and `positions.py` (automatic stop-loss/take-profit/trailing exits) call `risk.py::record_trade_executed()` — both count toward the same `MAX_DAILY_TRADES`, and both count a PENDING order (submitted, still live at the exchange after the fill poll) as well as a confirmed fill, since nothing ever observes the later fill to count it retroactively; only a `canceled` order, which never reached the market, is uncounted — and both call `monitoring.record_trade_result()` (every outcome, for the daily summary) and `monitoring.record_alpaca_order_outcome()` (only outcomes from an order actually submitted to Alpaca, for consecutive-failure tracking).
- `src/utils/monitoring.py`: tracks API call volume and Finnhub's rolling calls-per-minute (warning at `FINNHUB_RATE_LIMIT_WARNING_FRACTION` of `FINNHUB_RATE_LIMIT_PER_MINUTE`), Claude token usage per call, and Alpaca order success/failure; runs the three service health checks `main.py::run()` gates on; and logs a full daily summary (API calls per service, trade outcomes, token usage, every warning/error, start-vs-end portfolio value) the first time a new Eastern trading day is detected. Beyond that baseline tracking it raises four independent early warnings, each with its own `config.py` threshold: `log_claude_usage()` flags any single `generate_signal()` call whose total tokens exceed `CLAUDE_TOKEN_WARNING_THRESHOLD` (an unexpectedly large prompt); `record_alpaca_order_outcome()` flags `MAX_CONSECUTIVE_ALPACA_FAILURES` back-to-back failed order submissions; `record_portfolio_value()` flags a portfolio drop of more than `RUN_PORTFOLIO_DROP_WARNING_PCT` between two consecutive `run()` cycles, as an earlier/softer signal than `risk.py`'s `DAILY_LOSS_LIMIT_PCT` halt; and `check_zero_trade_streak()` (called from `main.py::run()` with the count of trades filled that cycle) flags `MAX_CONSECUTIVE_ZERO_TRADE_RUNS` cycles in a row with zero fills, which more often points at a configuration problem (confidence threshold too strict, a silently-bad API key) than a genuine dry spell. `send_metric_to_cloudwatch()` is a structured logging placeholder. Only `generate_daily_summary()` actually emits through it today (one metric per service, one per trade-outcome status, plus daily token usage and end-of-day portfolio value); the per-call counters elsewhere in the module accumulate in `_MonitoringState` and reach the log via that daily rollup rather than as individual metrics. So swapping its body for `cloudwatch.put_metric_data(...)` is still a one-function change, but it only ships the daily rollup until more call sites emit.

**`RISK_LEVEL` (`src/config.py`)**: a single 0.0–1.0 dial. `compute_risk_params(risk_level)` piecewise-linearly interpolates `stop_loss_pct`, `take_profit_pct`, `min_confidence`, `max_position_size_pct`, `max_daily_trades`, `daily_loss_limit_pct` across three anchor points each (0.0 / 0.5 / 1.0), since the ranges aren't symmetric around the midpoint. `RISK_LEVEL = 0.5` is the default and reproduces this system's original hand-tuned values exactly. The derived values are assigned to individually-named constants (`STOP_LOSS_PCT`, etc.) that can still be overridden by editing their own line — doing so detaches only that one parameter from `RISK_LEVEL`. `MAX_OPEN_POSITIONS`, `TRAILING_STOP_TRIGGER_PCT`, and the confidence brackets in `CONFIDENCE_POSITION_SIZE_TIERS` are deliberately *not* scaled by `RISK_LEVEL` — they're fixed diversification/tiering rules rather than risk-per-trade dials.

**DynamoDB persistence layer (`src/data/db.py`)**: `_DailyState` (in `risk.py`), `_trailing_stop_active` (in `positions.py`), and `_MonitoringState` (in `monitoring.py`) are still process-local, in-memory singletons for the running process, but every mutation is now also written through to DynamoDB and reloaded on the first call of a new Eastern calendar day (which also covers process startup), so a same-day restart no longer silently zeroes the daily trade counter, lifts a loss-limit halt, reverts trailing stops to plain stop-losses, or drops that day's monitoring counters. `risk.py` and `positions.py` write through on every mutation, since `halted_for_loss` is safety-critical; `monitoring.py` only checkpoints once per `run()` cycle (via `persist_state()`), since that state is pure observability. A fourth table, `trading-trade-history`, is a new append-only audit log of every `TradeResult` (written from `monitoring.record_trade_result()`, called by both `executor.py` and `positions.py`) — the one thing this system never durably recorded before. All persistence is best-effort and write-behind: every `db.py` function catches boto3/botocore errors internally, the boto3 client uses short timeouts and no retries so an outage fails fast, and DynamoDB health is deliberately **not** part of `monitoring.run_health_checks()` — persistence being down is never a reason to stop trading or stop protecting open positions. Tables are created once via `scripts/setup_dynamodb.py`, never automatically on app boot. Set `DYNAMODB_ENABLED=false` to disable persistence entirely (e.g. for local runs without AWS credentials).

**Gotcha — market hours**: outside 9:30–16:00 America/New_York on a weekday, `run()` is a no-op by design. Don't mistake that silence for a bug when testing. `market_hours.py::is_market_hours()` is only the cheap local pre-filter (weekday + clock, no holiday calendar), so it exists to avoid burning an API call overnight and at weekends; `is_market_open_per_alpaca(client)` is the authoritative gate `run()` gates orders on, since it reads Alpaca's own exchange calendar and therefore knows about holidays and early closes. If that clock call itself fails it falls back to `is_market_hours()` rather than returning False — a transient Alpaca error must not suspend stop-loss protection on open positions.

`signals.py::generate_signal()`'s user-message template labels the headlines with `news.py::NEWS_LOOKBACK_HOURS` (currently 4) rather than a hardcoded figure, so the label Claude sees always matches the real lookback window `get_stock_news()` filters to.

**Gotcha — Finnhub's free tier doesn't include historical candles**: `/stock/candle` for US equities now requires a paid Finnhub plan (confirmed via `finnhubio/Finnhub-API#546`) — a free key gets `{"error": "You don't have access to this resource."}` on every call. That's why `market.py::get_market_data()` still uses yfinance for the multi-day history `technical.py` needs; Finnhub is only used for the single-day `/quote` snapshot and `/company-news`, both of which are free-tier.

**Health-check ordering**: `main.py::run()` checks Alpaca health (`monitoring.check_alpaca_health()`) first and, if it fails, skips the entire cycle — without Alpaca neither position protection nor new trades are possible. Next, still before any trading, it confirms the exchange is actually open via `is_market_open_per_alpaca(client)` (see the market-hours gotcha below) and skips the cycle on a holiday or after an early close. If both pass, `check_open_positions()` and the daily-loss-limit check run next, both Alpaca-only. Only then does `monitoring.run_health_checks()` (Finnhub + Anthropic) gate the new-signal ticker loop. So a Finnhub or Anthropic outage no longer suspends stop-loss/take-profit/trailing-stop protection on existing positions — it only blocks the search for new trades — while an Alpaca outage still halts everything, since nothing in this pipeline can act without it.

## Issue log

Every real problem found so far and how it was resolved, oldest first. Add to this when you hit a new one — the point is that nobody has to rediscover these.

1. **Finnhub `/stock/candle` is paid-only for US equities.** Free keys get "You don't have access to this resource." Fix: historical bars stay on yfinance; Finnhub only does `/quote` and `/company-news` (both free).
2. **Health-check ordering suspended stop-losses.** A Finnhub or Anthropic outage used to skip the whole cycle, including position protection. Fix: Alpaca health is checked first and alone; Finnhub/Anthropic only gate the search for new trades (see "Health-check ordering").
3. **News window mislabeled.** The prompt hardcoded a lookback that didn't match `get_stock_news()`'s actual filter. Fix: the prompt reads `NEWS_LOOKBACK_HOURS` directly.
4. **Trailing stop reverted after a failed exit.** The breakeven flag was cleared before the exit order was confirmed, so a rejected or pending exit dropped the stop back to `-STOP_LOSS_PCT`. Fix: clear it only on a confirmed `FILLED` exit.
5. **PENDING orders weren't counted toward `MAX_DAILY_TRADES`.** The cap could be exceeded. Fix: PENDING counts as well as FILLED; only `canceled` doesn't.
6. **Holidays and early closes weren't respected.** The local clock check knows nothing about the exchange calendar. Fix: `is_market_open_per_alpaca()` is the real gate, falling back to the local check if Alpaca's clock call fails.
7. **Claude output could be truncated.** Opus 5's adaptive thinking draws from `max_tokens`, so 4096 risked cutting off the structured output. Fix: `max_tokens=16000` with `effort: "low"`.
8. **Risk checks didn't short-circuit.** `check_daily_loss_limit` ran (and could latch `halted_for_loss`) even on signals already rejected for being out of hours. Fix: each check is a lambda, so it runs only if every earlier check passed.
9. **NaN RSI on flat-price data.** 0/0 average gain/loss produced NaN, which reached Claude as "RSI: nan". Fix: `calculate_indicators()` raises on any non-finite value, and the ticker is skipped for that cycle.
10. **`signal.risk_level` looked like it affected sizing but doesn't.** Fix: documented as advisory only, and deliberately left unwired until there's trade history to validate it against.
11. **API keys were present but empty in `.env`.** Every cycle failed the health checks, so no ticker was ever analyzed, and it looked like "no signals" rather than an error. Fix: filled in the keys. When a run is silent, check the keys are non-empty before suspecting the code.
12. **(2026-10-09) Calling `run()` directly logged almost nothing.** Logging is only configured in `setup_logging()`, which only the `__main__` block calls. Fix: added `python -m src.main --once` for manual single cycles.
13. **(2026-10-09) The volume ratio was biased low on every ticker, every cycle.** During market hours yfinance's last daily bar is today's partial session, so partial-day volume was compared against full-day averages (0.24–0.81x at 1pm, near zero in the morning). Claude cited "low volume, no conviction" in nearly every HOLD. Fix: `calculate_volume_analysis()` drops the in-progress bar, which gave 0.73–1.44x on the same data. Confidences rose slightly, but on the first market-hours day nothing reached the 0.70 gate (best: TSLA/QQQ BUY at 0.60–0.62). Watch whether 0.70 is ever reached across several sessions before tuning the threshold or prompt.
