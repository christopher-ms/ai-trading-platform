# Issues & Test History

A running record of every real problem this system has hit, how it was fixed, and every real test run, so nobody has to rediscover any of it. **Add to this whenever you hit a new issue or run a new test.**

## Issues

Numbered oldest first. Each says what went wrong, why it mattered, and how it was fixed (or why it's still open).

1. **Finnhub `/stock/candle` is paid-only for US equities.** Free keys get "You don't have access to this resource." Fix: historical bars stay on yfinance; Finnhub only does `/quote` and `/company-news` (both free).
2. **Health-check ordering suspended stop-losses.** A Finnhub or Anthropic outage used to skip the whole cycle, including position protection. Fix: Alpaca health is checked first and alone; Finnhub/Anthropic only gate the search for new trades (see "Health-check ordering").
3. **News window mislabeled.** The prompt hardcoded a lookback that didn't match `get_stock_news()`'s actual filter. Fix: the prompt reads `NEWS_LOOKBACK_HOURS` directly.
4. **Trailing stop reverted after a failed exit.** The breakeven flag was cleared before the exit order was confirmed, so a rejected or pending exit dropped the stop back to `-STOP_LOSS_PCT`. Fix: clear it only on a confirmed `FILLED` exit.
5. **PENDING orders weren't counted toward `MAX_DAILY_TRADES`.** The cap could be exceeded. Fix: PENDING counts as well as FILLED; only `canceled` doesn't.
6. **Holidays and early closes weren't respected.** The local clock check knows nothing about the exchange calendar. Fix: `is_market_open_per_alpaca()` is the real gate, falling back to the local check if Alpaca's clock call fails.
7. **Claude output could be truncated.** Opus 5's adaptive thinking draws from `max_tokens`, so 4096 risked cutting off the structured output. Fix: `max_tokens=16000` with `effort: "low"`.
8. **Risk checks didn't short-circuit.** `check_daily_loss_limit` ran (and could latch `halted_for_loss`) even on signals already rejected for being out of hours. Fix: each check is a lambda, so it runs only if every earlier check passed.
9. **NaN RSI on flat-price data.** 0/0 average gain/loss produced NaN, which reached Claude as "RSI: nan". Fix: `calculate_indicators()` raises on any non-finite value, and the ticker is skipped for that cycle.
10. **`signal.risk_level` looked like it affected sizing but doesn't.** Fix: documented as advisory only, and deliberately left unwired until there's trade history to validate it against.
11. **API keys were present but empty in `.env`.** Every cycle failed the health checks, so no ticker was ever analyzed, and it looked like "no signals" rather than an error. Fix: filled in the keys. When a run is silent, check the keys are non-empty before suspecting the code.
12. **(2026-10-09) Calling `run()` directly logged almost nothing.** Logging is only configured in `setup_logging()`, which only the `__main__` block calls. Fix: added `python -m src.main --once` for manual single cycles.
13. **(2026-10-09) The volume ratio was biased low on every ticker, every cycle.** During market hours yfinance's last daily bar is today's partial session, so partial-day volume was compared against full-day averages (0.24–0.81x at 1pm, near zero in the morning). Claude cited "low volume, no conviction" in nearly every HOLD. Fix: `calculate_volume_analysis()` drops the in-progress bar, which gave 0.73–1.44x on the same data. Confidences rose slightly, but on the first market-hours day nothing reached the 0.70 gate (best: TSLA/QQQ BUY at 0.60–0.62). Watch whether 0.70 is ever reached across several sessions before tuning the threshold or prompt.
14. **(2026-10-09) Open positions are unprotected whenever the loop isn't running.** Stop-loss, take-profit, and trailing-stop exits are all checked by `check_open_positions()` inside `run()`; nothing is placed at Alpaca's side. So stopping the loop, closing the terminal, a crash, or a reboot leaves every open position with no stop at all. Also, the loop is still worth running on days when no signal reaches 0.70, because it's the only thing protecting existing positions. **Status: stop-loss half fixed 2026-10-10, first confirmed on a real position 2026-10-13** (META, see test history): every long position now gets a resting GTC stop order at Alpaca (`src/trading/backup_stops.py`), at the bot's own effective stop level (−`STOP_LOSS_PCT` from entry, moved to breakeven once the trailing stop activates). It's placed as soon as a BUY fills, and each cycle resyncs it (placed if missing, moved, resized if the position grew, orphans canceled). Exits and SELL signals cancel it first, because a resting stop holds the shares and Alpaca would reject the sell. If the exit fails, the stop is put back. Only orders tagged `backup-stop-` in `client_order_id` are ever touched. Take-profit is still bot-only. The other half, keeping the bot itself running, is the AWS move.
15. **(2026-10-09) `check_open_positions()` is silent when nothing triggers.** It only logs when it closes a position, so a healthy check and a check that never ran look identical in the log. **Status: open, minor.** Worth a one-line per-position status log at INFO.

16. **(2026-10-09) The laptop delayed a loop cycle while a position was open.** Cycles ran 14:21 → 15:15 → 15:46, so one gap was 54 minutes instead of 30. The Windows power log shows the laptop going in and out of Modern Standby all afternoon, the low-power state Windows uses when the screen turns off. That throttles background processes like the loop. Turning off idle sleep (`powercfg /change standby-timeout-* 0`) was **not enough**: standby was entered again at 15:06, after the change. **Status: fixed 2026-10-12 by moving the bot to an AWS EC2 server** (PROJECT_LOG step 31). A laptop can't be trusted to run it unattended, even with sleep disabled.
17. **(2026-10-09) The PC clock runs about 2 minutes slow compared with Alpaca's.** Both fills were stamped by Alpaca about 1m50s before our log's timestamps. Minor, because `is_market_open_per_alpaca()` (Alpaca's clock) is the real trading gate; only the local `is_market_hours()` pre-filter and the log timestamps are off. **Status: open, minor.** Sync the Windows clock (Settings → Time & language → Sync now); the AWS server will use NTP automatically.
18. **(2026-10-13) A second BUY on a stock already held is rejected by Alpaca as a "potential wash trade".** At 14:05 ET, an hour after the bot bought 6 META, Claude gave another META BUY at 0.71. `risk.py` approved it (no check stops adding to a position the bot already holds), but Alpaca rejected the order (`40310000`, "opposite side market/stop order exists") because the resting backup stop (issue 14) is a sell order for the same symbol. Logged as one `ERROR` trade outcome. **Harmless:** no order was placed, the existing position and its stop were untouched, and the loop carried on. The rejection is arguably the right outcome, since it stops the bot from doubling a position. **Status: open, deliberately deferred** until after a week of uninterrupted live running (decided 2026-10-14). Options then: reject a BUY in `risk.py` when the symbol is already held (cleanest, and stops a pointless Alpaca error), or allow adds by canceling the backup stop first and letting the reconcile step re-place it for the larger quantity. Each one also counts toward `MAX_CONSECUTIVE_ALPACA_FAILURES`, so a stock that keeps getting BUY signals while held could trip that warning.
19. **(2026-10-24) The new `trading-bot-offline` alarm fired within two minutes of `terraform apply`, although the bot was logging normally.** A CloudWatch metric filter only counts log lines that arrive after it's created, and the `TradingBot/LogLines` metric doesn't exist until the first counted line. So the alarm's first evaluation (01:30 UTC) found 90 minutes with no data, which it treats as breaching. The bot's last line had been at 00:45 UTC. The filter pattern (empty, which matches every line) was fine: `aws logs test-metric-filter` matched the "Market is currently closed" line. **Status: no fix needed.** The next line (01:45 UTC) was counted and the alarm went back to OK at 01:46 UTC. Expect the same one-off ALARM email after any re-create of the filter or alarm.
